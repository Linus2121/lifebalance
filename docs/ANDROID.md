## Windows setup
Install Node.js 22+ and Android Studio 2025.2.1+ with Android SDK Platform 36 and the bundled Java runtime. From the repository root:

```powershell
npm ci
npm run android:sync
npm run android:open
```

In Android Studio let Gradle sync finish, connect an Android phone with USB debugging enabled, select it and press Run. Repeat `npm run android:sync` after web changes. The mobile build copies only approved client assets into ignored `www/`; never point Capacitor at a remote server URL. The native app does not register the web service worker. Signing keys and local SDK settings are ignored by git.

## Step 2 implementation update — 2026-10-29
Native adapter now uses Capacitor Local Notifications for appointment, workout, meal and hydration schedules generated by the existing reminder engine (including multiple offsets). It reconciles pending alarms after saves/imports and when the app resumes; removed/edited alarms are cancelled and new ones scheduled. Snooze actions open the app and schedule a 10-minute or 1-hour delay. Notification details stay generic unless the user enables details. A private notification channel hides lock-screen contents by default (users can change Android channel settings).

The Settings page in native builds shows native scheduling state instead of requiring a web server. A 15-second test alarm is provided. Scheduling success is not represented as proof of real delivery. The plugin restores scheduled alarms after reboot; that path remains untested on devices. Time-zone changes are reconciled on resume; alarms already queued are absolute instants until then. The horizon remains 45 days / 300 reminders; users must reopen the app to replenish it. No exact-alarm permission is requested in this phase; inexact delivery may be delayed by Android, idle modes and manufacturer restrictions. Force-stop can prevent notifications until the app is opened again.

Native exports now use a cache file and the Android share sheet; users choose a destination. JSON imports use the existing native file chooser, validation, record-count confirmation and pre-import restore copy. Native import/export and destination file access still need phone testing. Temporary exports contain private records and remain in the app-private cache until cleared by Android; they are not durable backups. The browser's existing data stays in the browser.

`.github/workflows/android.yml` provides an unsigned-for-release debug APK build with Java 21 and SDK 36 on GitHub Actions. This workflow has no production signing keys. It must successfully run before an installable APK is claimed. Native compilation was not possible in this workspace because SDK download approval was blocked. Android Studio has not been installed on the user's laptop. Existing source-level tests plus four native scheduling tests pass (45 total).

Still pending: phone tests (foreground/background/closed/reboot/DST/permissions/snooze/accessibility/migration), store signing, full secure credential storage and account configuration, pricing and store submission. Native scheduling is not a medical or emergency alarm service.

## Custom audio ringtone — 2026-10-29
Version 1.0.2 (code 3) adds a prominent Custom ringtone: choose audio file button and Use device tones. Import uses Android's document picker; only the selected file is read (no broad storage permission). Android 10+ required for import. Audio must be playable, at most 30 seconds, and at most 5 MB. Cancel, invalid files and import errors keep the current tone. Successful import copies the audio into the tablet's shared Notifications/LifeBalance folder; it is not uploaded and is not included in JSON backups. Removing that copy can stop custom sound playback.

A hash-based notification category is created for each distinct custom audio clip because Android prevents changing the sound of an existing category programmatically. Reselecting a category respects its user-configured mute/sound settings. On tone change, pending reminder alarms are reconciled onto the chosen category, including test alerts and snoozes; selecting Use device tones returns to the existing default reminder category. Old categories/media remain available in Android settings. Device audible playback/import and update compatibility remain to be verified. A visible Android app version badge helps identify the installed APK.

## Missed-appointment investigation — 2026-10-29
User reported an appointment alert missing at 20:40. Cause is not yet confirmed on the tablet. Review found the earlier builds deliberately used inexact alarms, and default appointment offsets are one day and 30 minutes before (no due-time alarm unless At event time is selected).

Version 1.0.4 (code 5) adds optional SCHEDULE_EXACT_ALARM special access (not USE_EXACT_ALARM). Allow precise reminder timing opens Android's permission screen on user request. Reconciliation checks access on each sync/resume and upgrades/downgrades queued alarms accordingly. Granted precise timing uses exact/allow-while-idle scheduling; no grant keeps explicitly labelled inexact alarms. Force-stop, permission revocation, manufacturer restrictions, Do Not Disturb and muted channels can still affect delivery. No guaranteed delivery is claimed.

Settings shows the last successful queue check, number of registered future reminders, the next five registered alert times with the device time zone, a muted-category warning and a shortcut to app notification/battery settings. After scheduling, queued IDs/metadata are read back before success is displayed. This confirms plugin registration, not that Android actually displayed or sounded an alarm. Missing registrations and startup errors are surfaced. A custom-tone query failure falls back to the base reminder category instead of blocking all scheduling. No existing appointment or reminder offsets are silently changed.

Required retest on the tablet: allow notifications and precise timing, create an appointment five minutes ahead with At event time selected, verify that time in Next registered alert times, leave the app on the Home screen and observe. Repeat locked-screen, snooze and edited/cancelled appointments. The reported 20:40 delivery failure remains unverified until these tests run.


Follow-up clarification (2026-10-29): the user confirmed At event time was NOT selected for the 20:40 appointment. Therefore a reminder at 20:40 itself was not requested by that appointment; earlier offsets do not imply a due-time alarm. This explains the missing due-time alert but does not independently verify delivery of any earlier alert. Retesting must explicitly select At event time. Source checks now pass 52 tests.
